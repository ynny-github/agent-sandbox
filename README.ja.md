# agent-sandbox

[English](README.md) | **日本語**

AI コーディングエージェント (Claude Code) を [nono](https://github.com/tkancf/nono)
サンドボックス内で動かし、エージェントが発行するすべてのシェルコマンドを、
専用の兄弟 nono セッションで動くホスト側コマンドブローカー経由で仲介します。
それぞれのコマンドが何に触れてよいかは、オペレーターが書く nono の
コマンドプロファイルだけが決めます — `agent-sandbox.toml` の関心事では
ありません。

目的はエージェントをマシンから締め出すことではなく、境界を *明示的に、
検査可能に* することです。`agent-sandbox ai explain` は、どのコマンドが
専用のサンドボックスで動き、どのコマンドがブローカー自身の許可の下で
直接動くのか、そしてどの拒否がなぜ発生したのかをエージェントに伝えます。
ポリシーによる拒否は「ポリシーによる拒否」として読め、原因不明の失敗として
再試行されることはありません。

```
launcher
├── nono wrap  --profile <エージェント用プロファイル>    -- claude …   ここにコマンド制御は無い
└── nono run   --profile <コマンドプロファイル>          -- agent-sandbox broker
                                                            │
                                                            ├─ exec git → shim → git、専用の子サンドボックス
                                                            │                     └─ exec ssh → shim → ssh、これも専用
                                                            └─ exec rg  → ブローカー自身のサンドボックスで直接実行
```

2 つのセッションは兄弟関係であり、決して入れ子にはなりません。間に
シェルは挟まりません: ブローカーはエージェントのコマンドラインをそれ自身で
解釈し (パイプライン、`&&`/`||`/`;`、リダイレクト、グロブ、`$(…)`、
`for`/`if`、`cd` などの組み込みはすべて動きます)、単純コマンドはそれぞれ
直接 exec します。`bash` と `sh` はそれ自身が宣言されたコマンドであり、
専用の子サンドボックスを持ち、セッションから到達可能です — シェルを直接
呼び出すことも `git` と同じように仲介されます。いったん起動した
ツールチェーンがその後も自力で到達できるものだけの話ではありません。
そのツールチェーンについての注意点が何を今もカバーしているかは
[2 つのプロファイル](#2-つのプロファイル) を参照してください。

## 必要なもの

- `PATH` の通った [nono](https://github.com/tkancf/nono) — サンドボックスエンジン本体
- Go 1.25 以降 (ソースからビルドする場合)
- `PATH` の通った `claude` — `agent-sandbox claude` を使う場合

`agent-sandbox doctor` で確認できます。

## インストール

```bash
go install github.com/ynny-github/agent-sandbox@latest
```

[mise](https://mise.jdx.dev/) を使う場合:

```toml
# .mise.toml
[tools]
"go:github.com/ynny-github/agent-sandbox" = "latest"
```

**インストールしたバイナリは、コマンドプロファイルが書き込みを許可する
すべてのパスの外に置く必要があります。** そうしないと nono はセッションの
起動を拒否します
(`tool-sandbox policy command binary is replaceable through writable parent directory`)。
プロジェクト自身の作業ディレクトリ内に置いたビルド成果物は、それが
エージェントの作業領域である以上この条件を満たしません。`agent-sandbox`
をポリシーコマンドとして宣言するコマンドプロファイルを書く前に、
安定した、プロジェクト外のパスにインストールしてください
(`go install` が既定でそうします)。

## クイックスタート

プロジェクトルートに `agent-sandbox.toml` を書きます — これは 2 つの
プロファイルファイルの名前を挙げるだけで、中身は作りません:

```toml
tool_mode = "hook"

[agents.claude]
profile = "claude-profile.json"   # エージェントプロセス自身の nono プロファイル。あなたが書く
```

そのうえで、両方のプロファイルを自分で nono 自身のスキーマで書きます:
`claude-profile.json` (エージェントプロセス自身のサンドボックス — 詳しくは
[エージェント用プロファイル](#エージェント用プロファイル-agentsnameprofile) 参照)
と、`command-profile.json` (ブローカー経由のすべてのコマンドのサンドボックス —
詳しくは [2 つのプロファイル](#2-つのプロファイル) 参照) です。どちらにも
既定値はありません: ファイルが無ければ起動エラーになり、agent-sandbox は
どちらの中身も生成も読み取りも検証もしません (パス以外は)。

両方が解決できることを確認してから起動します:

```bash
agent-sandbox doctor            # nono・ブローカーソケット・両方のプロファイルはすべて使えるか
agent-sandbox ai config-check   # agent-sandbox.toml は解決できるか、両方のプロファイルは検証を通るか
agent-sandbox claude -- --model opus
```

`sandbox up` のような事前準備は不要です。`agent-sandbox claude` はホスト側の
コマンドブローカーを専用の nono セッション内で起動し、Claude をもう一つの
兄弟セッションの下で立ち上げ、Claude の終了時にブローカーを片付けます。

## 仕組み

### ブローカーはルーターではなく、サンドボックス化されたプロセスである

`agent-sandbox claude` は 2 つの兄弟 nono セッションを起動します:
1 つは `[agents.<name>].profile` が指す *オペレーターが書いた*
エージェント用プロファイルの下で Claude Code を包み、もう 1 つは
*オペレーターが書いた* コマンドプロファイルの下で `agent-sandbox broker` を
実行します。どちらのプロファイルも生成されたものではありません — どちらも
あなたが nono 自身のスキーマで書くファイルであり、agent-sandbox はそのパスを
`nono` に渡すだけです。2 つのセッションは兄弟であり、入れ子ではありません
— nono はサンドボックスの中にサンドボックスを入れ子にすることを拒否するため
であり、だからこそブローカーはエージェント自身のセッションの中では
動きません。

エージェントが発行するすべてのシェルコマンドは unix ソケット経由で
ブローカーに届きます。ブローカーはシェルではありません: 組み込みの
インタプリタでコマンドラインをそれ自身で解釈し、単純コマンドごとに直接
`execve` を呼びます。コマンドラインを `bash -c` に渡す方式 — このプロジェクトが
以前採用していた設計 — は、修正不能であることが分かりました:
`git reset --hard` に対して書いた拒否ルールは、git を名前ではなく
`/nix/store` のパスで直接呼び出すだけで簡単に破られますし、nono 自身の
ドキュメントも、`exec` を汎用シェルに向けることはサンドボックスを
無効化すると明言しています。この設計には、そもそも破るべきシェルが
存在しません。

### 2 つの階層

コマンドプロファイルは、実行され得るすべてのプログラムを 2 つの階層の
どちらかに振り分けます:

- **ポリシーコマンド** は、専用の子サンドボックスとともに
  プロファイルへ宣言されます — このリポジトリ自身のプロファイルでは
  `git`、`ssh`、`bash`、`sh`、`go` です。どれも nono の `invocation_policy`
  argv ルールは持ちません。それぞれを縛るのは、呼び出し元エッジごとに
  決まる自分自身のファイルシステム・ネットワーク・環境変数の許可です
  (実例は [2 つのプロファイル](#2-つのプロファイル) を参照)。ブローカーが
  これらを実行に回すのは nono 自身が生成する shim 経由だけです — 絶対パス
  やシンボリックリンク、その他 shim を迂回するどんな手段によっても回しま
  せん。この保証はブローカー自身がどう実行に回すかについてのものであり、
  *別の* コマンド自身のサンドボックスがなお到達し実行できてしまうものを
  保証するものではありません — 詳しくは後述します。
- **それ以外すべて** はブローカー自身のサンドボックスの中で直接動き、
  そのサンドボックスのファイルシステム・ネットワーク・実行許可が許す
  範囲に従います。これらのコマンドを列挙したリストはありません:
  ブローカー自身はポリシーコマンドではないため、どの
  プログラム名を実行に回してよいかをプロファイルの何かが縛っている
  わけではありません。Tool Sandbox が有効化されると、ブローカー自身の
  実行許可は `PATH` 上の信頼済みディレクトリから組み立てられます —
  このプロファイルでは `/nix/store`、`/run/current-system/sw`、
  mise がインストールしたツールチェーンなどです — そして、名前のリスト
  ではなくこの許可の集合こそが、第一階層に含まれないものすべてに対する
  境界です。

ポリシーコマンドからの拒否は必ず自分自身を説明します:
拒否は、そのプロファイルエントリの `from` エッジが書いた `reason` を
運びます。フロアで失敗するコマンドは、代わりに素の `execve` 権限の
失敗になります — `Permission denied` か「no such file」で、未知の
コマンドと同じように、示すべき `reason` フィールドはありません。

どちらの階層もカバーしないものが 1 つあります: ブローカー自身のシェル
組み込みコマンド (`echo`, `cd`, `test`, `read`、その他組み込みインタプリタ
が実装するもの) は、ブローカープロセス自身の中で、ブローカー自身の
ファイルシステム許可のもとで動きます — どちらの階層も経由しません。
あなたが書くリダイレクトやグロブも同じように制限されます。

**また、どちらの階層も、コンパイラやインタプリタが実行時に何をするかを
縛るものでもありません。** ここで列挙されているのは、コードを実行できる
すべてのプログラムではなく、専用サンドボックスを持つ 5 つのコマンドだけ
です。しかもその 5 つに含まれること自体は、それだけで狭い境界を意味しま
せん: コードをコンパイルして実行するツールチェーンを縛るのは、あくまで
*それ自身の* プロセスが到達できる範囲だけです — それが `python` や
`rustc` のようにフロアで動くプロセスであっても (このリポジトリ自身の
プロファイルはどちらもポリシーコマンドとして宣言していません)、あるいは
`go` のようにここではポリシーコマンドであっても、縛られるのはやはり
自分自身のサンドボックスの到達範囲だけです。argv ルールによってでも、
プロファイルの他の箇所でどのツールが宣言されているかによってでもあり
ません。それが実際どれだけの代償を伴うかは、下の
[2 つのプロファイル](#2-つのプロファイル) を参照してください。`go` も
例外ではありません。

### ファイルシステムは仮想化されない

コンテナも bind マウントもありません。コマンドはホストのファイルシステム上で
*同じ絶対パス* のまま、自分自身のサンドボックス (ポリシーコマンドの場合) か
ブローカーのサンドボックス (フロアコマンドの場合) が許可する範囲に制限されて
実行されます。`HOME` は実際の値のままです。エージェントが見るものと
コマンドが実際に触れるものとの間で、パスを変換する必要は一切ありません。

コマンド自身の許可の外にあるパスは、そのプロファイルエントリが明示した
場合にだけ到達できます。

### どちらのプロファイルも agent-sandbox のものではない

agent-sandbox は nono プロファイルを一切生成しません。起動エージェント自身の
プロファイル (`[agents.<name>].profile` が指すもの) も、ブローカー経由の
すべてのコマンドが動くコマンドプロファイルも、どちらもオペレーターが
nono のスキーマで直接書くファイルです。agent-sandbox はそのパスを解決して
`nono` に渡すだけです。詳しくは
[エージェント用プロファイル](#エージェント用プロファイル-agentsnameprofile) と
[2 つのプロファイル](#2-つのプロファイル) を参照してください。

## コマンド

| コマンド | 内容 |
|---|---|
| `agent-sandbox claude -- [claude の引数...]` | コマンドブローカーを兄弟セッションとして起動した状態で、nono 下に Claude を立ち上げる |
| `agent-sandbox exec -- <command>` | コマンドを 1 つブローカーへ送り、出力をストリームする |
| `agent-sandbox doctor` | `nono` が動作するか、このホストで実際に Tool Sandbox を起動できるか、ブローカーソケットが bind できるか、両方のプロファイルが存在し検証を通るか、コマンドプロファイルが固定しているパスがすべて存在するか、エージェント用プロファイルが `AGENT_SANDBOX_BROKER_SOCKET` を転送するか、コマンドプロファイルが自身のバイナリへの書き込みを許可していないかを確認。exit 0 / 1 |
| `agent-sandbox debug -- [claude の引数...]` | 実行はせずに、両セッション分の `nono` コマンドと GitHub MCP 設定 (トークンは伏字) を表示 |
| `agent-sandbox ai explain` | サンドボックスの、エージェント向け説明 — コマンドがどう動くか、2 つの階層、各拒否の理由 |
| `agent-sandbox ai config-check` | 起動時と同じ手順で `agent-sandbox.toml` と両方の nono プロファイルを検証 |
| `agent-sandbox command-router` | MCP サーバーを起動 (`tool_mode = "mcp"`) |
| `agent-sandbox hook` | PreToolUse アダプタ (`tool_mode = "hook"`。Claude が呼ぶもので、手で叩くものではない) |

グローバルフラグ: `--config <path>` (既定 `agent-sandbox.toml`) と `--env <ref>`
(繰り返し指定可)。

`claude` と `debug` では、`--` の前に置けるのは `--config` と `--env` だけです。
`--` の後ろはすべて `claude` に渡ります。`agent-sandbox` は `nono` にオプションを
転送しません — 両方のプロファイルは設定ファイルと、それが指すコマンド
プロファイルから決まります。

`--settings` は `agent-sandbox` が予約しており、パススルーオプションとして拒否
されます。GitHub MCP が有効なときは `--mcp-config` / `--strict-mcp-config` も
拒否されます。

### `doctor`

`doctor` は起動が依存する事柄を確認します。

- `nono` が `PATH` にあり、`nono --version` が動作すること。
- **このホストで実際に Tool Sandbox を起動できること。** `nono` バイナリが
  存在すること自体はこれを何も保証しません: nono はいずれにせよ起動し
  バージョンを表示しますが、`command_policies` が実際に Tool Sandbox を
  有効化した時点で初めて拒否することがあります。doctor は最小限のプローブ
  用プロファイルの下で、本物の使い捨て `nono run` セッションを実行して
  この問いに直接答えます — 例えば、NixOS 上で自身の ELF 依存関係チェーンを
  解決できない未パッチの nono を検出できます。この失敗は、そうでなければ
  セッション内で最初の本物のコマンドが同じように失敗するまで見えないまま
  になります。
- コマンドブローカーが、ソケットディレクトリ (`$XDG_STATE_HOME/agent-sandbox`、
  未設定なら `~/.local/state/agent-sandbox`) で実際に **unix ソケットを bind
  できる** こと。単なる書き込みチェックでは不十分で、bind することで
  `sun_path` の約 104 バイト制限も検出できます。
- 2 つの nono プロファイル — エージェント用プロファイル
  (`[agents.<name>].profile`) とコマンドプロファイル — がどちらも存在し、
  `nono profile validate` を通ること。
- エージェント用プロファイルが `AGENT_SANDBOX_BROKER_SOCKET` をサンドボックス
  内へ転送すること。doctor はこの変数にセンチネル値をセットし、
  `nono wrap --profile <エージェント用プロファイル>` の使い捨てセッションを
  1 つ起動して、そのセンチネルが生き残るかを確かめます。nono に直接尋ねる
  ことはできません: `nono profile show` は `environment.allow_vars` を
  報告せず、`nono why` には環境変数を問い合わせるクエリもありません。その
  ため読むのではなく計測します。この変数が無いとエージェントは決して
  ブローカーへ到達できず、すべてのコマンドが、画面上には何の説明もない
  理由で失敗します。doctor 自身がセッション内で動いている場合はスキップ
  されます — nono はサンドボックスの中にサンドボックスを入れ子にすることを
  拒否するため、このプローブはホスト側で実行してこそ意味を持ちます。
- コマンドプロファイルが自身のバイナリへの書き込みを許可していないこと —
  doctor は `nono why --profile <コマンドプロファイル> --path <ブローカーの
  バイナリ> --op write` を尋ね、答えが allowed なら失敗にします。
- **コマンドプロファイルが `command_policies` の下で固定しているパスは
  すべてチェックされますが、同じ基準では判定されません。** doctor は
  プロファイルの `executable_dirs`、各ポリシーコマンドの `executable`、
  そして `exec_paths` の各エントリが指すパスを nono に尋ね、パスが
  無くなったときに nono がどう失敗するかでグループ分けします:
  `executable_dirs` のエントリが無い場合と `executable` のピンが無い
  場合は、どちらも起きた瞬間に報告されます — 前者は nono がセッションの
  起動そのものを拒否するため、後者はそのコマンドの仲介を無言のまま完全に
  無効化するためです。無効化されると nono は最初に見つかった `PATH`
  上のものにフォールバックしてそれを *セッション自身* の許可で実行し、
  `nono profile validate` はそれでも通り、監査ログには "tools: active,
  no invocations" としか残りません (nono 0.74.0 で実測) — 完全に無言では
  なく、nono は警告を出力し `--silent` はそれを抑制しませんが、その警告は
  大量の起動出力の中では見落としやすく、そこで名指しされる危険は実在
  します。一方 `exec_paths` のエントリが無い場合は nono が仕様どおり
  無言でスキップするため、それ自体は報告されません: あるコマンド自身の
  `exec_paths` は、そのセット全体のエントリが *すべて* 無くなったときに
  初めて報告されます。それまではそのコマンドにまだ到達可能なヘルパー
  ディレクトリが残っているからです。これこそが、同じヘルパー
  ディレクトリについて複数のもっともらしい場所を並べた候補リスト (1 つの
  プロファイルが複数種類のホストで動けるようにするためのもの) を、
  doctor の誤検知ではなく正当なものにしています — このリポジトリ自身の
  `git` エントリがまさにそうした候補リストを持つ実例については、下の
  実例を参照してください。NixOS ではこれらのパスがすべて store ハッシュ
  を含むため、通常のパッケージアップグレードだけで
  `executable_dirs`/`executable` の故障モードは起こり得ます — これが、
  この
  リポジトリ自身のプロファイルがそもそも `executable` を一切固定しない
  理由でもあります ([2 つのプロファイル](#2-つのプロファイル) 参照)。

どれか 1 つでも失敗する場合、`agent-sandbox claude` は Claude を起動しません。

## 設定

### `tool_mode`

エージェントのコマンドがブローカーに届く経路を選びます。

| モード | 挙動 |
|---|---|
| `hook` | Bash と Monitor は有効のまま。起動時に `claude --settings` 経由で PreToolUse フックが注入され、各コマンドが `agent-sandbox exec -- <command>` に書き換えられる。`.claude/settings.json` には何も書き込まれない。`agent-sandbox` が `PATH` にある必要がある |
| `mcp` (既定) | Bash と Monitor を無効化。エージェントは `run_command` MCP ツール経由でコマンドを実行し、出力は `mcp.command_output_dir` 配下のファイルに書かれる — レスポンスにはパスと exit code のみが載る |

hook モードでは、Bash 呼び出しとエージェント自身のサンドボックスの間に立って
いるのはこのフックだけです。そのため失敗の 2 経路をどちらも塞いであります:

- **フックは動いたが書き換えられない場合** — ペイロードが読めない、JSON が壊れて
  いる、command が入っていない — は **exit 2** で終わります。Claude Code が
  ブロックとして扱う唯一のコードで、理由は stderr 経由でエージェントに返ります。
  それ以外の非ゼロ終了は「非ブロッキングなエラー」として扱われ、元のコマンドが
  書き換えられないまま、エージェント自身のサンドボックスで、コマンドプロファイル
  の制約を一切受けずに実行されてしまいます。
- **フックがそもそも起動できない場合** — 例えばエージェントのプロファイルが
  そのバイナリに届いていないとき。これはフックの中からは捕まえられないので、
  ランチャが先に証明します: エージェントに制御を渡す前に、エージェント自身の
  サンドボックス内でフックをプローブ用ペイロードで 1 回実行し、コマンドが
  書き換わって返ってこなければ起動を拒否します。`agent-sandbox debug` は同じ
  呼び出しを表示します。

mcp モードにはどちらの失敗もありません。Bash と Monitor が最初から無効なので、
迂回する先が存在しないからです。


```toml
tool_mode = "hook"

[mcp]
command_output_dir = "/tmp/mcp-output"  # mcp モードでは必須。hook モードでは無視される
```

コマンドプロファイルはブローカー起動時に一度だけ読まれます —
`agent-sandbox.toml` の編集と同じく、これを編集しても効果が出るのは次回の
`agent-sandbox claude` からで、セッション途中で反映されることはありません。

### エージェント用プロファイル: `[agents.<name>].profile`

起動されるエージェントプロセス自身が動く nono プロファイルは、オペレーターが
nono 自身のスキーマで書くファイルです。agent-sandbox はその中身を生成も
読み取りも検証もしません — `[agents.<name>].profile` が指すパスを解決して
`nono wrap --profile` に渡すだけです。テーブルのキーは起動サブコマンドの
名前です: `agent-sandbox claude` は `[agents.claude]` を読みます。

| 書き方 | 解決先 |
|---|---|
| 省略 | `agent-sandbox.toml` のそばの `<name>-profile.json` |
| 相対パス | `agent-sandbox.toml` を含むディレクトリを基準に結合 |
| 絶対パス | そのまま |

```toml
[agents.claude]
profile = "claude-profile.json"
```

プロファイルファイルが無ければ起動エラーです: 生成される既定値はありません
— コマンドプロファイルの挙動と同じです。このファイルが何を許可すべきかは
[2 つのプロファイル](#2-つのプロファイル) を、`~/.config/agent-sandbox/config.toml`
にこのキーを書いたときの挙動は
[ユーザースコープ設定](#ユーザースコープ設定) を参照してください。

ランチャだけが値を知っている 4 つの grant は、このファイルに書きません。
`nono wrap` のコマンドラインで渡されます:

| grant | なぜ動的か |
|---|---|
| `agent-sandbox` バイナリ自身 (`--read-file`) | エージェントは `agent-sandbox hook` と `agent-sandbox serve` を自分の直接の子として — broker 経由ではなく自分のサンドボックス内で — 実行する。mise 管理のツールチェーンではバイナリのパスに Go のバージョンが入るので、アップグレードで番号が変わる |
| worktree の main git ディレクトリ (`--allow`) | 起動ごとに検出する |
| 生成された GitHub MCP 設定 (`--read-file`) | 毎回新しい一時ファイル |
| コマンドブローカーのソケット (`--allow-unix-socket`) | 名前がランチャの PID から作られる |

1 つ目が無いと nono は execve を拒否し、画面に何の説明も出ないままあらゆる
コマンドが失敗します。そのためランチャは自分のバイナリの位置が分からない
場合、起動そのものを拒否します。

このファイルは手書きであるため、nono のスキーマが許す任意のパスを指定
できます — `bypass_protection` を使えば `~/.aws`、`~/.gnupg`、
`~/.config/gh`、`~/.kube` のような保護対象プレフィックスも指定できます。
削除された capability カタログが提供していたのは固定の組み合わせだけ
でした。どちらのプロファイルファイルも、他のコードと同じように
`git diff` でレビューする価値があります。

### 2 つのプロファイル

すべてのホストアクセスは、オペレーターが nono 自身のスキーマで書く 2 つの
ファイルで決まります — agent-sandbox はどちらも生成せず、パスを渡すだけです:

- **エージェント用プロファイル** (`[agents.<name>].profile`。
  [上記](#エージェント用プロファイル-agentsnameprofile) 参照) は、起動される
  エージェントプロセス自身が動くサンドボックスです: そのファイルツールと、
  直接の子プロセスとして立ち上げる MCP サーバーが対象です — エージェントが
  立ち上げる MCP サーバーはブローカー経由ではないため、Python 製や Go 製の
  MCP サーバーなら、そのランタイムもここで許可する必要があります。シェル
  コマンドはここでは一切動きません。
- **コマンドプロファイル** (以下で説明) は、ブローカー経由の *すべての*
  コマンドが動くサンドボックスです — Bash/Monitor 経由 (hook モード) でも
  `run_command` MCP ツール経由 (mcp モード) でも、ブローカーに届くものは
  すべてここです。

どちらか一方に書いたものが、もう一方に届くことはありません。エージェント
プロセス自身はシェルコマンドを一切実行しません — hook モードでは
Bash/Monitor は PreToolUse フック経由でブローカーへ回されますし、mcp モード
では Bash そのものが無効化されています。だからこそ、**コマンドを実行する
ためだけに必要なものは、エージェント用プロファイルには一切書きません**:
`go` や `python` などのツールチェーンへの許可はコマンドプロファイルの
仕事であり、ここには要りません。エージェント用プロファイルに残るのは本当に
狭い範囲だけです — このリポジトリ自身の `claude-profile.json` が実例です。

`AGENT_SANDBOX_BROKER_SOCKET` はエージェント用プロファイルの
`environment.allow_vars` に含めなければなりません。これが無いとエージェント
はブローカーに一切到達できず、あらゆるコマンドが何も名指さないエラーで
失敗します。`agent-sandbox doctor` はこれを直接計測します
([`doctor`](#doctor) 参照) — nono には尋ねられません: `nono profile show`
は `environment.allow_vars` を報告せず、`nono why` には環境変数を問い合わせる
クエリもありません。

`command-profile.json`。nono 自身のスキーマで書き、`agent-sandbox.toml` の
そばに解決されます — TOML のトップレベルで `command_profile = "<path>"` を
書けば名前を上書きでき、相対パスは TOML を含むディレクトリを基準に解決
されます。ファイルが無ければ起動エラーです: 生成される既定値は存在しません。
静的な既定値ではホストごとの違い (`/nix/store` か `/usr/bin` か) を吸収
できませんし、「存在しているように見えて実はすべてのコマンドを拒否する」
プロファイルは最悪の壊れ方だからです。

`agent-sandbox` がこのファイルから読むのは、`ai explain` が 2 つの階層を
説明する (「[仕組み](#仕組み)」参照) のに必要な分と、`doctor` が検証に
通り自身のバイナリへの書き込みを許可していないことを確認するのに必要な
分だけです。それ以外のすべての判断 — どのコマンドが存在するか、それぞれが
何に触れてよいか、どの呼び出しを拒否するか — はオペレーターのもので、
nono のスキーマで直接表現されます。

**`$WORKDIR`。** nono は `filesystem` の中と、すべての `command_policies`
子サンドボックスの中でこれを展開します。作業ディレクトリを意味する箇所には
リテラルなパスではなく必ずこれを書いてください — これが 1 つのプロファイルで
複数の git worktree を扱えるようにする仕組みです。

**ネットワーク。** トップレベルの `network` セクションは上限です。
`network_profile` か `allow_domain` を設定すると、nono はループバック
プロキシを立ち上げ、プロキシ用の環境変数
(`http_proxy`/`HTTP_PROXY`/`https_proxy`/`HTTPS_PROXY`/`no_proxy`/`NO_PROXY`) を注入します。
`block: true` や `network_profile: null` はプロキシを一切立ち上げません。
生の Landlock のレベルでは、command_policies の子コマンド自身の `network`
は、実測したところ許可の状態が実質 2 つしかありません: キーを省略すると
完全に遮断され (`network: {}` もキー省略と同じ挙動)、`{"allow_all": true}`
と `{"allow_domain": [...]}` はどちらもソケットを開くという同じ許可を
与えます。`allow_domain` が意味するはずの「ドメインでの制限」自体は
Landlock のチェックではありません — それを実際に強制しているのは
もっぱら nono 自身のプロキシであり、だからこそそれはグラント自体では
なく、プロキシ用の環境変数がその子コマンドまで実際に届くかどうかに
懸かっています (下記)。

子コマンドのトラフィックが、その `network` 付与が意味するとおりに実際に
絞られるかどうかは、その付与自体とは無関係で、プロキシ用の環境変数が
その子コマンドまで届くかどうかで決まります。各ホップは呼び出し元から
受け取った環境変数を自分自身の `environment.allow_vars` でフィルタします。
チェーンのどこか 1 か所のホップ (セッション自身のトップレベルの
`environment` セクションを含む) がプロキシ変数を省略すれば、それより
下のすべてのホップにとってその変数は消えており、リーフは直接の、
仲介されない接続にフォールバックします: プロキシ変数が届かない
`allow_domain` はそのドメインに絞られておらず、プロキシ変数のない
`allow_all` は文字通り無制限であり、「上限まで」ではありません。

**`git` 自身のネットワーク付与は GitHub に絞られており、HTTPS
トランスポートだけを対象にします。** その子サンドボックスは `network:
{"allow_domain": ["github.com", "*.githubusercontent.com"]}` を設定して
おり、トップレベルの `network` (上限) も同じ 2 つを許可しているため、
プロキシは実際にその手前に立ち上がっています。セッション自身のトップ
レベルの `environment.allow_vars` と `git` 自身のそれの両方が、プロキシ
用の 6 つの変数名 (`http_proxy`/`HTTP_PROXY`/`https_proxy`/`HTTPS_PROXY`/
`no_proxy`/`NO_PROXY`) を運んでおり、これで十分であることは実測済みで、
`NONO_*` 系の変数を追加する必要はありませんでした。実際のブローカーを
通して実測したところ、`git ls-remote https://github.com/git/git.git HEAD`
は本物の ref を返しましたが、`git ls-remote https://example.com/x`、
生の IP、存在しないドメインはいずれも `CONNECT tunnel failed, response
403` という、DNS や経路の失敗ではなく本物のプロキシ拒否で、同じように
失敗しました。どちらかのホップの `allow_vars` からプロキシ変数を省けば、
これは静かにインターネット全体へ再び開いてしまいます。このプロファイルを
変更するときは、触った 1 か所だけでなく両方のホップを確認してください。
SSH リモートはこの付与を一切経由しません — 下の `ssh` という別コマンドを
経由して出ていきます。

**`ssh` 自身のネットワーク付与は `{"allow_all": true}` であり、`git` の
付与とは違って、これは本当に無制限です。** SSH プロトコルは nono の
HTTP(S) プロキシを通してトンネルできないため、ここで `allow_domain` を
指定しても拒否されますし、`allow_all` を絞り込むためのプロキシもそもそも
存在しません。`nono profile validate` はこのエントリに対して
`[allow_all_network]` の警告を出しますが — プロキシのチェーンが実際に
絞り込んでいるグラントに対する警告とは違い — この警告は文字どおりに
受け取るべきです: `ssh` はどんなホストにも到達できます。実際にこれを
縛っているのは、このエントリの他のすべての部分です: `ssh` は `git`
からしか到達できません (`session: "deny"` がセッションからの直接呼び出し
を拒否し、exit 126 になります)。そしてファイルシステムの許可は狭く —
`~/.ssh/id_main`、`~/.ssh/config`、`~/.ssh/known_hosts` の読み取り、
`~/.ssh/known_hosts` の書き込みだけです。このホストには紐付けられる
生きた `ssh-agent` の資格情報がありません (`SSH_AUTH_SOCK` はもう存在
しないソケットを指しています) ので、鍵ファイル自体が、本来なら nono の
`credentials` の仕組みが代わりに提供するはずの許可になっています。

**`bash` と `sh` は `network` キーを一切持たず、その不在自体が拒否です**
— `allow_domain` や `allow_all` で「親切に」埋めるべき見落としではあり
ません。どちらも `$WORKDIR`、nix store、`/run/current-system/sw`、
mise がインストールしたツールチェーンに読み取りと実行の両方で限定されて
おり、ネットワークにはどんな形でも到達できません。実測したところ、
`~/.ssh/id_main` も `~/.gitconfig` も、どちらのサンドボックスの内側からも
拒否されます。

**git のフックは `git` のサンドボックス内では実行されません。**
`git commit` は `git commit --no-verify` として実行しない限り
`fatal: cannot exec '.git/hooks/commit-msg': Permission denied` で失敗
します — そしてそのために、**コミットメッセージの検証はこのサンドボックス
の内側では動きません**: 壊れたメッセージを捕まえるフックがそこには無い
ので、コミットする前に自分で正しく書いてください (このリポジトリは
Conventional Commits に従います。`.claude/rules/git-commit.md` 参照)。
フックを実行できるようにするには `$WORKDIR` と `/nix/store` を `git`
自身の `exec_paths` に追加する必要があります — フックのシェバンは、
git 自身のフックファイルへの `execve()` の一部として、カーネルに
`/nix/store` の下のインタプリタを exec させます。このプロファイルは
意図的にそれをしていません: `$WORKDIR` はエージェントが書き込め、
`git` のサンドボックスはすでにネットワークアクセスとグローバル
gitconfig への読み取りアクセスを持っているため、それを広げると、
エージェントが書いたコンテンツが作業ツリーに現れた瞬間、git がそれを
ネットワーク付きで任意実行できてしまいます — 書き込んでから実行する
経路です。しかもそれは、そこまでのコストを払っても検証を取り戻せません:
別途、フックを一時的に有効にして実測したところ、`lefthook` はやはり
動かず、このリポジトリ自身の Conventional Commits ルールに違反する
コミットメッセージが検証されないまま通りました。フックが実行されるか
どうかにかかわらず、正味の効果は同じです: コミットメッセージの検証は
このサンドボックスの内側では動かないので、フックの実行を再び開くことは
その代償に見合いません。

**実例** — このリポジトリ自身のルート直下の `command-profile.json` は、
5 つのポリシーコマンドを宣言しています: `git`、`ssh`、
`bash`、`sh`、`go` です。このリポジトリ自身のワークフローが使うそれ以外
すべて (`rg`、`mise`、`gofmt`、coreutils、…) はフロアで動きます —
`command_policies` ではなく `groups.include` とトップレベルの
`filesystem`/`environment` セクションを通じて許可されています。

この 5 つはどれも `executable` を固定していません。存在しないパスへの
ピンはそのコマンドの仲介を完全に無効にします: nono は最初に見つかった
`PATH` 上のものにフォールバックし、それを *セッション自身* の許可で
実行し、`nono profile validate` はそれでも通り、監査ログには
"tools: active, no invocations" としか残りません (nono 0.74.0 で実測)。
これは無言ではありません — nono は警告を出力し、`--silent` はそれを
抑制しません — が、その警告は大量の起動出力の中では見落としやすく、
危険は実在します。`git` の実バイナリは nixpkgs の更新のたびに変わる
`/nix/store` パスなので、ここで固定すると次のアップグレードで `git` が
サンドボックスから外れてしまいます — これが `doctor` の「profile paths」
チェック
([`doctor`](#doctor) 参照) が存在する理由でもあり、代わりにこの
プロファイルが実際に固定しているパス (各コマンド自身の `exec_paths`)
を検証します。

- **`git`** はセッションから到達可能で、実バイナリをそのまま直接実行し
  ます — ラッパーも第二の名前もありません。その子サンドボックスは
  `$WORKDIR`、オブジェクトストア (`@git:common-dir`、`@git:worktree`、
  `@git:toplevel`、`@git:hooks-path`)、グローバル/システムの git config
  (`@git:config-files`。nono はこれを、それらのスコープの中の
  `include.path`/`includeIf.*.path` が宣言する対象だけに解決します —
  `local` と `worktree` スコープは除外されるので、リポジトリは自分自身の
  `.git/config` を通じてホストへのアクセスを自分に与えることはできません)
  への読み取りアクセスを与え、さらに `exec_paths` の下に
  `libexec/git-core` を持ちます — これは HTTPS トランスポート専用の
  別バイナリ `git-remote-https` のためだけに必要です。nono は
  `exec_paths` のエントリが無くても静かにスキップするため、nixpkgs の
  git 更新でこのパスが動くと、プロファイルを名指しする診断なしに HTTPS
  トランスポートが壊れます — これはまさに `doctor` の「profile paths」
  チェックが捕まえるものです。`exec_paths` にはこの `/nix/store` パスと
  並んで `/usr/lib/git-core` と `/usr/libexec/git-core` も並んでいます
  — このリポジトリ自身の NixOS ホストではどちらも存在せず、nix のハッシュ
  が古くなった場合と同じようにスキップされますが、Nix でないホストでは
  存在し (そのため使われ)、HTTPS トランスポートが NixOS 専用にならずに
  済みます。`git` 自身の `can_use: ["ssh"]` こそが
  `ssh` が到達可能である唯一の理由です — 両コマンドのネットワーク付与と
  git フックのトレードオフについては上の
  [ネットワーク](#2-つのプロファイル) を参照してください。
- **`ssh`** は `git` からしか到達できません。セッションからの直接呼び出し
  は拒否されます (`session: "deny"`、exit 126)。
- **`bash` と `sh`** はセッションからしか到達できません。意図的に `git`
  からは到達できません — `git` はそもそもフックを一切実行できない
  (上記) ため、どちらかへの `git` 呼び出し元エッジは無駄になるからです。
  どちらも `can_use: ["go"]` を宣言しており、`go` 側にも対応する
  `from.bash`/`from.sh` エッジがあるため、`go build`/`go test`/
  `go version` はどちらのシェルの中からも動きます — これは意図的に
  `go` 自身の `from.session` エッジより狭いエッジです (ネットワークなし)。
  シェルの中から `go` を経由することが、`bash`/`sh` 自身の
  ネットワーク無しというルールを回避する抜け道になってはならないから
  です。
- **`go`** はセッションから直接、また `bash`/`sh` の呼び出し先として
  (上記) 到達可能です。その自分自身のサンドボックスは、モジュール
  キャッシュ・ビルドキャッシュ・チェックサムデータベース用に
  `~/go/pkg/mod`、`~/go/pkg/sumdb`、`$XDG_CACHE_HOME/go-build` を許可し、
  `$WORKDIR` と `/tmp` には書き込みと実行の両方を許可します (`go test`
  は `/tmp` にバイナリをコンパイルして即座に実行するため)。そして
  `from.session` エッジに限り、`proxy.golang.org` と `sum.golang.org`
  へのネットワーク到達を許可します — これはこのプロファイル自身の
  トップレベル `network.allow_domain` に既にある、同じ 2 つのホストです。
  これがなぜ存在し、何を代償にしているかは、下の「3 つの事実」の
  リストを参照してください。

この 5 つはどれも `invocation_policy` の argv ルールを一切持ちません。
このプロジェクトの以前のリビジョンでは、無条件の `push --force` や
`reset --hard` などをブロックする git 固有のルールを、実バイナリを
exec する前に各呼び出しを解析する Go 製のラッパーを通じて強制していま
した。そのラッパー (`internal/safe/git`。`agent-sandbox` バイナリ自身の
`safe` サブコマンド経由で起動される) は今も存在し、今もビルドされ、
今もテストされていますが、このプロファイルはもうそれを組み込んでいません:
上の `git` のエントリは実バイナリを直接 exec し、argv レベルのポリシーは
一切ありません。**このプロファイルで `git` を縛っているのは、もっぱら
そのファイルシステム・ネットワーク・`can_use` の付与が届く範囲だけです
— どの git サブコマンドやフラグが渡されたかではありません。** これらの
argv レベルのルールを取り戻したいオペレーターは、ラッパーを明示的に
組み込み直す必要があります (`git` の `executable` を `agent-sandbox`
バイナリに固定し、`argv_prepend: ["safe", "git"]` を追加し、実バイナリに
そのラッパー経由でしか到達できない第二の名前を与える) — これはこの
リポジトリ自身のプロファイルが下していない能力判断です。

これら 5 つのコマンドのエッジのどれも、nono の `sandbox` 省略記法
(`"from": {"session": {"sandbox": {...}}}` という長い形の代わりに
`"from": {"session": "sandbox"}`) では書かれていません。nono はどちらの
形も同じように実行しますが、`nono why --command` はこの省略記法を実装
していません: このプロファイルに対して尋ねると、実際には動いている
コマンドについて DENIED、`from.session` が無いという理由を返します
(nono 0.74.0 で実測) — そして `agent-sandbox ai explain` はエージェント
にまさにその問い合わせを実行するよう伝えるため、省略記法で書かれた
エッジは、エージェントに見抜く手段の無い偽の拒否を渡してしまいます。
このプロファイルのすべてのエッジが長い形で書かれているのはこのためです。

**`docker` はこのリポジトリのプロファイルには一切宣言されていません** —
どのポリシーコマンドのエントリにも名前がありません。
`docker` ラッパー (`internal/safe/dockercompose` と `cmd/safe_docker.go`:
`docker` → ラッパー → `realdocker` → 実バイナリ — このプロファイルが
`git` を上で説明した直接サンドボックスへ移す前に `git` 自身のエントリが
使っていたのと同じ argv 解析パターン) は完全に実装されテストも済んで
いますが、コマンドプロファイルへ組み込むかどうかはオペレーターが意図的に
下す能力判断であり、このリポジトリのプロファイルを真似れば済む話では
ありません。理由は Docker ソケットにあり、見た目どおりではありません:

> **Docker ソケットはファイルシステムで制限されていません。** nono は
> パス名形式の AF_UNIX ソケットを一切仲介しません — 仲介するのは Linux の
> *アブストラクト* ソケット名前空間だけです。そのため
> `/var/run/docker.sock` は、`fs_read`/`fs_write` に何を与えていようが
> いまいが、`docker` バイナリを実行できるどんなコマンドからも到達できます。
> `docker` を宣言しないままにしておいても、ブローカーがそれを実行に回すこと
> 自体は止まりません: 宣言されていないコマンドは子サンドボックスも
> `can_use` エッジも argv ゲートも一切持たず、他のどのフロアコマンドとも
> 同じようにブローカー自身の許可の下で直接動きます — 信頼済みの `PATH`
> ディレクトリに載ってさえいれば到達できます ([2 つの階層](#2-つの階層)
> 参照)。このリポジトリ自身のプロファイルに対して直接実測したところ、
> `docker --version` は実行されます — ブローカーはそれを実行に回します —
> そして 255 で終了するのは、nix の `docker` パッケージ自身の `bin/docker`
> スタブが `libexec` への re-exec に失敗するからであり、tool-sandbox の
> 拒否によるものではありません。ソケットは、`docker` がプロファイルに
> 一度でも登場するかどうかにかかわらず、すでにこのプロファイルのフロアから
> 到達可能です。`docker` を宣言すること (下のラッパーとともに) が加えるのは
> argv レベルのチェックであって、もともと存在しないファイルシステムの境界を
> 新たに作るわけではありません — 作るべき境界がそもそも無いからです。
> 宣言した場合、ラッパーのチェック (下記) がファイルシステムの境界の背後に
> ある第二の防御層ではなく、*唯一の* 防御になります。デーモンに到達できる
> こと自体が root 相当だからです: このソケットはコンテナに `/` を
> マウントすることを許してしまいます。ソケット自体を制限するには
> `linux.af_unix_mediation` と `filesystem.unix_socket` の許可リストが
> 必要です — nono のプロファイルガイドが `no-docker` の例で説明している
> 別個の opt-in であり、このリポジトリのプロファイルはこれを設定していません。
> `docker` を一切宣言していないからです。

ラッパーのチェックで十分だと判断したオペレーターは、次の形で組み込め
ます:

```json
"docker": {
  "executable": "<agent-sandbox バイナリ>",
  "can_use": ["realdocker"],
  "from": { "agent-sandbox": { "sandbox": {
    "argv_prepend": ["safe", "docker"],
    "...": "..."
  } } }
},
"realdocker": {
  "executable": "/nix/store/…-docker-…/libexec/docker/docker",
  "from": { "docker": { "sandbox": { "...": "..." } } }
}
```

それをする前に知っておくべきことが 3 つあります。第一に、上の
`executable` は意図的に `bin/docker` ではなく `libexec/docker/docker` に
なっています: NixOS では `bin/docker` は絶対パスで `libexec/docker/docker`
に re-exec するだけの小さなスタブで、nono のコマンドごとの Landlock ルール
セット (固定した実行ファイル自身の直接的なライブラリ依存関係から構築される)
はこの間接的に呼び出される第二のパスを許可しません — スタブを固定すると
すべての呼び出しが黙ってクラッシュします (`execve(...) = -1 EACCES`、
"Command exited with code 255" としか報告されません)。第二に、ラッパーの
チェック (`internal/safe/dockercompose` と `cmd/safe_docker.go`。正確で
最新のルールセットはソースを読んでください — `--help` は実 docker に
そのまま通り、ラッパーのルールセットではなく docker 自身のヘルプを
表示します: 通常の `docker` の経路では、ラッパーが自分自身のフラグ解析を
無効にしているためそもそも横取りされず、`compose` の経路では、
`--help` を見た時点でモデル解決自体を丸ごとスキップします —
ヘルプは何も実行しないので、モデルを必要としないからです) は argv・
モデルレベルであり、ファイルシステムレベルではありません: `compose` の
呼び出しは *解決済みの* モデル (`docker compose config`) に照らして
チェックされます — ホストパスのマウント、Docker ソケット、`privileged`、
ホストの `network`/`pid`/`ipc`、危険な capability、無効化された
seccomp/apparmor。それ以外のすべての呼び出しは argv レベルで `run`/`exec`、
`--privileged`、ホストパスまたは Docker ソケットへのバインドマウントを
チェックします。

第三に、これが上のソケットの事実を踏まえると最も重要です:
ラッパーのチェックには既知の抜け穴が 2 つあり、どちらも docker がそもそも
到達不能だったからこそ許容されていました — この opt-in ブロックを貼り
付けた瞬間、その前提は失われます。
- `docker create` の後に `docker start` を実行すると、個々の呼び出しの
  どちらにも危険なフラグが現れないまま `docker run` と同じ実行状態に
  到達します — `create` 自体は拒否対象ではありません (コンテナを作成
  するだけで起動しないこと自体は危険ではないからです)。これは 1 回の
  呼び出しで argv チェックが閉じられる構文上の欠陥ではなく、2 回の
  呼び出しにまたがる構造的な抜け穴です。
- `--mount type=volume,volume-opt=device=...,volume-opt=o=bind` は実質的に
  バインドマウントです (`o=bind` を伴う `local` ドライバのボリュームは
  `device` のパスへのバインドマウントとして振る舞います) が、mount の
  チェックは `type=bind` だけをキーにしているため、`type` が `volume`
  であるこの形式は捕まえられません。

このリポジトリのどちらも閉じられていません。docker を有効にするオペレー
ターは、誰かがこれらを閉じるまでの間、両方を受け入れることになります。

この設計が拠り所にしている事実が 3 つあります。どれも nono 0.74.0 で
実測しています:

- **Tool Sandbox が有効化される以上、`go` を自分自身のポリシーコマンド
  として宣言する必要があります。そうしないと Go のツールチェーンが自分
  自身のツールを exec できません。** `command_policies.commands` の
  エントリが 1 つでも宣言される (`git` 単独でも十分です) と、ブローカー
  自身の実行許可は `PATH` 上の信頼済みディレクトリから組み立て直され
  ます。Go のツールチェーンの内部ツール (`compile`、`link`、…) は
  `PATH` 上には存在しないため、その mise 管理のディレクトリを名指しする
  許可がないと、`go build ./...` は
  `fork/exec .../pkg/tool/linux_amd64/compile: permission denied` で
  失敗します (`go` エントリを外して同じコマンドを再実行して実測)。この
  リポジトリのプロファイルは以前、トップレベルの
  `command_policies.executable_dirs` エントリでそのディレクトリを直接
  名指しすることでこれを解決していました — リテラルパスのみ
  (`executable_dirs` は `~` も `$HOME` も展開しません)、マイナー
  バージョンに固定 (`.mise.toml` は `go = "1.25"` を指定: パッチ
  アップグレードでは壊れませんが、マイナーバンプでは派手に壊れます)。
  今はその代わりに `go` をポリシーコマンドとして宣言しています。
  `executable_dirs` ではこの仕事を最後まで終えられなかったからです:
  `go test` は `/tmp` にバイナリをコンパイルして即座に実行しますが、
  nono はグループ/他ユーザ書き込み可能なディレクトリを実行可能として
  扱うこと自体を拒否するため、`/tmp` は `executable_dirs` にはそもそも
  追加できませんでした。コマンドごとのポリシーが持つ自分自身の
  `exec_paths` には、どちらの制約もありません — 上の実例の `go` の
  項目を参照してください。
- **`executable` のピンが無くなると、そのコマンドの仲介が完全に無効に
  なります。だからこそこのプロファイルはどれも固定していません** (上の
  実例参照)。これは無言ではありません — nono は警告を出力し、
  `--silent` はそれを抑制しません — が、その警告は大量の起動出力の中
  では見落としやすく、危険は実在します。`agent-sandbox doctor` の
  「profile paths」チェックが存在するのは、固定されている `exec_paths`
  エントリが古くなることを捕まえるためであり、そもそも作られなかった
  ピンを捕まえるためではありません。
- **`nono why --command` は `sandbox` 省略記法を実装していません。だから
  こそこのプロファイルのすべてのエッジが省略形ではなく `from.session`
  で書かれています** (上の実例参照) — 省略記法は、実際には動いている
  コマンドに対して偽の DENIED を返しますし、`ai explain` はエージェントに
  まさにその問い合わせをするよう伝えます。

さらに知っておくべき性質が 2 つあります:

- **コードをコンパイルして実行するツールチェーンは、他にどのコマンドが
  宣言されているかによっても、どちらの階層に属するかによっても縛られ
  ず、それ自身のサンドボックスが届く範囲だけに縛られます。** `python` と
  `rustc` はこのプロファイルの 5 つのポリシーコマンドに含まれないため、
  どちらも他のすべてのフロアコマンドと同じブローカー自身のサンドボックス
  の中で直接動きます。`go` は 5 つのうちの 1 つですが、ポリシーコマンド
  であること自体はこの点について何も買い戻しません。縛られる先が
  狭くなるだけです: その自分自身のエッジは `$WORKDIR` と `/tmp` に
  書き込みと実行の両方を許可します。`go test` が `/tmp` にバイナリを
  コンパイルして即座に実行するからです。どちらの場合であっても、
  該当するサンドボックスのファイルシステムとネットワークの付与が届く
  範囲であれば、そこでコンパイルしてすぐに実行するプログラムも同じ範囲
  に届きます — 原理的には、このプロファイルが別の場所でサンドボックス化
  しているプログラムのコピーを `/tmp` や `$WORKDIR` 経由で作って exec
  することも含みます。2 階層モデルはこれを塞ぐためにあったことは一度も
  ありません: これが決めるのはブローカー自身が名前で何を実行に回すかで
  あり、コンパイルされたプログラムが直接 exec するバイナリは、そもそも
  ブローカーが実行に回すものではないからです。自分で書くプロファイルで
  コンパイラやインタプリタ自身のツールチェーンを列挙するなら、それ自身の
  サンドボックスが届く範囲を正直な境界として扱ってください。2 階層
  モデルの絶対性ではありません。
- **`nono profile validate` は JSON の構文とグループ参照だけを検証します**
  — スキーマの誤りすべてを検出するわけではありません (`exec_paths` 自体、
  公開されている JSON Schema には載っていませんが、ランタイムは尊重します)。
  `validate` が通ることだけでなく、実際のワークフローを実際の `nono run`
  セッションに対して検証してください。

### ユーザースコープ設定

任意の `~/.config/agent-sandbox/config.toml` がプロジェクト設定と合成
されます: すべてのフィールドはスカラーかスカラーのマップであり、
**プロジェクトファイルが書いたものはすべてそちらが優先されます** —
キーを省略すればユーザースコープの値にフォールバックします。

`[agents.<name>]` テーブルはキー単位でマージされます。和集合ではありません:
ユーザースコープファイルにだけ宣言されたエージェント (たとえば
`[agents.codex]`) は、プロジェクトファイルが `[agents.claude]` しか宣言して
いなくても、そのまま有効です。*両方の* ファイルに存在するテーブルは、
フィールド単位でマージされるのではなく、プロジェクト側のもので丸ごと
置き換えられます — 今日の時点で `AgentConfig` はフィールドを 1 つしか
持たないため、プロジェクトの `[agents.claude]` テーブルはそのエージェントの
プロファイルパスを常に完全に決定します。

これは `command_profile` がすでに持っているのと同じスカラー上書きの挙動
です: `command_profile` も、あらゆる `[agents.<name>].profile` も
「プロジェクトがユーザーを上書きする」値なので、「どのプロジェクトにも
そのそばに `claude-profile.json` がある」という規約をユーザースコープ
ファイルで一度だけ宣言でき、違うパスが必要なプロジェクトはそこだけ上書き
すればよいということになります。

## 環境変数 (`--env`)

`--env` は、Claude を起動する / コマンドを実行する前に、ファイルから環境変数を
*ランチャー自身の* プロセスに読み込みます。繰り返し指定でき、スキーム付きの
参照を取ります。現時点で存在するのは `file:` だけです。

```bash
agent-sandbox claude --env file:.env -- --model opus
agent-sandbox exec --env file:.env -- go test ./...
```

形式は dotenv の最小サブセットです: 1 行 1 つの `KEY=VALUE`、`#` コメントと
空行は無視、先頭の `export ` は除去、前後のクォートは削除。**変数展開はありません。**
値はホストの同名変数を **上書き** します。複数ファイルを指定した場合は後のものが
勝ちます。

**`--env` はもう何も許可しません。** 変数をランチャー自身のプロセスに
読み込むことと、サンドボックス化されたエージェントがそれを見られることは
別の話です: nono が転送するのは、オペレーターが手で書くプロファイルの
`environment.allow_vars` が挙げているものだけです。`--env` で読み込んだ変数が
起動エージェントに届くのは、エージェント用プロファイルの
`environment.allow_vars` にその名前がある場合だけです — `MISE*` のような
グロブを使えば、一群の変数を 1 行でカバーできます。同じ変数をブローカー
経由のコマンドにも渡したい場合は、コマンドプロファイルの
`environment.allow_vars` を別途、明示的に編集してください — ただし例外が
1 つあります: `AGENT_SANDBOX_BROKER_SOCKET` は、それにマッチするどんな
名前やワイルドカードであっても、コマンドプロファイルの
`environment.allow_vars` に **絶対に** 含めてはいけません。ブローカー
ソケットに到達できるコマンドはブローカーへ再帰でき、ブローカーは並行数の
上限なしにハンドラを spawn するため、ホスト側のフォーク爆弾になります。
値が黙ってエージェントに届かない、というのがまさにこの段落が防ごうとして
いる失敗です。

## GitHub MCP

組み込みの GitHub MCP サーバーは、`GITHUB_MCP_TOKEN` が空でないときに有効になります。
空の場合はそもそも設定されません。値は `GITHUB_PERSONAL_ACCESS_TOKEN` として MCP
サーバーに渡されます。

```bash
agent-sandbox claude --env file:.secrets.env -- --model opus
# .secrets.env の中身: GITHUB_MCP_TOKEN=ghp_...
```

`agent-sandbox debug` は、トークンを伏字にした MCP 設定を表示します。

## 開発

```bash
mise install          # Go と lefthook
go test ./...         # ユニットテスト + 統合テスト
go build ./...
mise run build         # `go install` で作業ツリーのビルドをインストール
```

**このプロジェクト自身のバイナリをビルドしても、もう `PATH` には乗りません。**
`agent-sandbox claude` は自分自身のブローカーのエントリポイントを、起動元
プロセスの `PATH` を通してベース名で解決します
([2 つのプロファイル](#2-つのプロファイル) 参照)。もし作業ツリー内に
ビルド出力を置いてしまうと、それはコマンドプロファイルが `fs_write` を
許可しているのと同じディレクトリに収まってしまい — nono がエントリポイント
のバイナリに対して拒否する、書き込み可能かつ実行可能という組み合わせに
なります。そこで `mise run build` はその代わりに `go install` を実行します。
これは `GOBIN` が設定されていればそこへ、なければ `$(go env GOPATH)/bin` へ
インストールします — いずれにせよ `$WORKDIR` の外で、すでに `PATH` に入って
います (このリポジトリの mise 管理下の Go プラグインは、その Go バージョン
専用の `bin/` を `GOBIN` に指定しています)。変更を試したいときは毎回
`mise run build` を実行してから、いつも通り起動してください
(`agent-sandbox claude`)。`go run .` はこの代わりにはなりません: 生成される
バイナリは実行時に `$TMPDIR` 以下に置かれ、プロファイルとの間に何の対応関係
もないからです。

E2E スイートは `e2e` (Python/pytest、MCP stdio) にあります。
